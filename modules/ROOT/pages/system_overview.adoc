[[system_overview]]
= System overview (non-normative)

The _RISC-V Debug Specification_ cite:[riscv-debug-spec-1.0] defines the concept of a Debug Transport Module (DTM) along with one specific implementation, the JTAG-DTM.
A DTM acts as a link between an off-chip interface to a Debug Module Interface (DMI), which is essentially a very simple bus that only supports 32-bit read/write accesses to a small address space.
This address space commonly contains one or more Debug Module (DM) instances, which provide the actual debug functionality for one or more RISC-V hardware threads (harts).

With the JTAG-DTM, a simplified view of the system is as follows:

[[fig_dtm_system]]
.RISC-V platform and debugger, simplified view
image::dtm_system.svg[]

This specification establishes an alternative to the JTAG-DTM that can operate at high speeds, offers robustness features and only uses two single-ended I/O pins.
To reduce duplication, it takes advantage of the fact that there already exists a perfectly viable specification for a RISC-V DTM, namely the JTAG-DTM.
The JTAG-DTM can conceptually be split into two parts, the JTAG transport and DMI bus manager:

[[fig_jtag_dtm]]
.JTAG-DTM split into two parts
image::jtag_dtm.svg[]

The JTAG transport implements the 4-pin JTAG interface, the state machine and shift registers that provide read-write access to three relevant registers, namely <<transactions.adoc#idcode_register,idcode>>, <<transactions.adoc#dtmcs_register,dtmcs>> and <<introduction.adoc#dmi_register,dmi>>.
In the context of the JTAG-DTM, the relevant operation is a read of one of these registers (Capture-DR state) followed by a write to the same register (Update-DR state).

The DMI bus manager implements these three registers and contains the state machine and other logic to access DMI subordinates.
It is specific to a particular implementation-defined DMI bus.

To implement a RISC-V Serial Debug Protocol DTM (RSDP-DTM), only the JTAG transport is replaced by a different transport that is reasonably simple, efficient and optionally robust in the presence of bit errors:

[[fig_tw_dtm]]
.Possible RSDP-DTM implementation
image::tw_dtm.svg[]

Reusing the existing JTAG-DTM register specification greatly simplifies the handling of DMI bus errors, needing no additional specification.
It is expected that it will be easy to convert an existing JTAG-DTM implementation into an RSDP-DTM implementation by replacing the JTAG state machine and shift registers, as opposed to requiring a new implementation for each DMI variant.

== RSDP-FAST and RSDP-ROBUST interface states

Both performance and robustness are important characteristics of a debug protocol. In some cases, however, increasing robustness comes with a trade-off in performance, and vice versa.

That is why this specification provides the choice between two interface states: <<interface_states.adoc#rsdp_fast_state,RSDP-FAST>> (with focus on performance), and <<interface_states.adoc#rsdp_robust_state,RSDP-ROBUST>> (with focus on robustness). == Option for compatibility with JTAG

Some RISC-V platforms will still need JTAG for compatibility with JTAG-only tools or for JTAG-only features such as boundary scan.
To take advantage of the RSDP protocol's robustness and to use the extra JTAG pins for functional I/O, a combined JTAG and RISC-V Serial Debug Protocol DTM (RSDPJ-DTM) can use the existing JTAG transport and a simple multiplexer, as in the following figure:

== RSDP protocol properties

*Simplicity* is provided by

* Reusing the semantics, in particular of bus error conditions, of the existing JTAG-DTM standard
* Enabling reuse of existing components, even sharing much of the physical logic in an RSDPJ-DTM
* A truly synchronous physical two-pin interface, without start/stop conditions as found in I2C/I3C or escapes as found in cJTAG
* A fixed request-response transaction format without variable delay and timeout condition in the response

*Efficiency* is provided by

* An efficient encoding that only transfers the data that is actually needed
* A line encoding that allows input/output register stages on I/O pins
* An ordering of operations that means that in most cases while a DMI bus transaction is in progress, the previous transaction's read data or the next transaction's write data can be transferred, virtually eliminating the need for artificial idle cycles or polling

*Robustness* is provided by

* Interface enabling patterns with at least 150 relevant bits
* Optional CRC, implemented such that the length of each transaction is deduced by CRC-protected information
* Facilities to recover from a detected transmission error without unintended DMI bus transactions or loss of data

*Flexibility* is provided by

* Option to focus on performance (<<interface_states.adoc#rsdp_fast_state,RSDP-FAST>> interface state) or robustness (<<interface_states.adoc#rsdp_robust_state,RSDP-ROBUST>> interface state)
* Option to operate in JTAG mode for legacy debuggers or JTAG-only features like boundary scan
* Option for single-pin debugging
* Option for debugging via the CAN physical layer
