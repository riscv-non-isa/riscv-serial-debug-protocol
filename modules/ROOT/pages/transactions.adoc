= Transactions

The basic unit of the protocol is the transaction, which in the error-free case consists of a request from the debugger followed by a response from the target.
The main purpose of a transaction is to perform a read of one of the three JTAG-DTM registers (<<idcode_register,idcode>>, <<dtmcs_register,dtmcs>> or <<introduction.adoc#dmi_register,dmi>>) and/or a write of the same register.
There also exists a <<nop_transaction,NOP>> transaction that does not perform any operation.

Refer to the RISC-V Debug Specification for the semantics of the <<idcode_register,idcode>>, <<dtmcs_register,dtmcs>> and <<introduction.adoc#dmi_register,dmi>> registers.

[[transaction_format]]
== Transaction format

A transaction is transmitted as follows (refer to <<introduction.adoc#wire_format>>):

[source,plaintext]
----
/ START / TT / WR-PAYLOAD / CRC / 0b0 /              -- Request from debugger
/ 0b0 / START / STAT / RD-PAYLOAD / CRC / 0b0 /      -- Response from target
/ 0b0 /                                              -- Debugger drives line
----

This corresponds to the following waveforms for the two RSDP states.
Note that <<wr_payload_field,WR-PAYLOAD>> and <<rd_payload_field,RD-PAYLOAD>> length depends on the transaction and may be zero.

[[figure_format_robust]]
.Waveform of an RSDP-ROBUST transaction
[wavedrom,target=robust_transaction,svg]
----
{signal: [
  {name: 'RCLK',            wave: '0.p..................................l'},
  {name: 'RDAT (debugger)', wave: '01.02...2..|2.....0z................0.', data: ['TT', 'WR-PAYLOAD', 'CRC']},
  {name: 'RDAT (target)',   wave: 'z..................01.02.2..|2.....0z.', data: ['STAT', 'RD-PAYLOAD', 'CRC']},
]}
----

[[figure_format_fast]]
.Waveform of an RSDP-FAST transaction
[wavedrom,target=fast_transaction,svg]
----
{signal: [
  {name: 'RCLK',            wave: '0.p..................l'},
  {name: 'RDAT (debugger)', wave: '012...2..|0z........0.', data: ['TT', 'WR-PAYLOAD']},
  {name: 'RDAT (target)',   wave: 'z..........012.2..|0z.', data: ['STAT', 'RD-PAYLOAD']},
]}
----

There is no variable gap between the request from the debugger and the response from the target.
The target must respond immediately if a valid request was received (constant fields and CRC as expected, valid <<tt_field,TT>> value) and otherwise enter an error state as described in <<error_handling.adoc#error_handling>>.
After the response from the target, the debugger must drive one `/ 0b0 /` to ensure that there is no drive conflict while the target stops driving the RDAT line.
It may drive any number of further `/ 0b0 /` idle cycles before the start of the next transaction request.

[[start_field]]
=== START field

The <<start_field,START>> field marks the start of a half-transaction, either from debugger to target or from target to debugger.

The response from a target starts with `/ 0b0 / START /` to ensure that the debugger receives a rising edge of the RDAT line driven by the target.
Without the extra zero, the timing of the rising edge would be determined by the I/O pin's tristate control, which could be different from the drive value path.

In <<interface_states.adoc#rsdp_robust_state,RSDP-ROBUST>> state, this field is encoded as `/ 0b011 /`.
Using multiple bits allows detection of a bit error inside this field.

In <<interface_states.adoc#rsdp_fast_state,RSDP-FAST>> state, this field is encoded as `/ 0b1 /`.

[[tt_field]]
=== TT field

The 4-bit <<tt_field,TT>> (transaction type) field encodes the different transactions, as described in <<transactions>>.
It is encoded as follows:

[[table_tt_encoding]]
.Encoding of the TT field
[%header,cols="1,5"]
|===
| <<tt_field,TT>>                     | encoding
| <<nop_transaction,NOP>>             | `0b0111`
| <<intbus_wr_transaction,INTBUS_WR>> | `0b0001`
| <<intbus_rd_transaction,INTBUS_RD>> | `0b1001`
| <<dmi_transactions,DMI_NOP>>        | `0b0100`
| <<dmi_transactions,DMI_WR>>         | `0b0010`
| <<dmi_transactions,DMI_RD>>         | `0b1010`
| <<dmi_transactions,DMI_WR_SA>>      | `0b0110`
| <<dmi_transactions,DMI_RD_SA>>      | `0b1110`
| Reserved                            | `0b0000`, `0b0011`, `0b0101`, `0b1000`, `0b1011`, `0b1100`, `0b1101`
| Illegal                             | `0b1111`
|===

The encoding `0b1111` must not be used to ensure that an escape sequence is always detected as an invalid transaction request.
For use of the encodings marked as _reserved_, see <<extensions>>.

NOTE: The encoding allows the target to decode whether the access is a DMI transaction from the least significant bit of `TT`.

In <<interface_states.adoc#rsdp_robust_state,RSDP-ROBUST>> state, the value of the <<tt_field,TT>> field specifies the type of the _following_ transaction.
This is required because the length of the <<wr_payload_field,WR-PAYLOAD>> and <<rd_payload_field,RD-PAYLOAD>> fields depends on the transaction type.
If the transaction contained its own type information, that information would have to be used before the CRC can be checked.
This would prevent the detection of some single-bit errors.
After an <<escape_sequences.adoc#enable_robust_sequence,ENABLE-ROBUST>> sequence, the following transaction is always a <<nop_transaction,NOP>> transaction.

In <<interface_states.adoc#rsdp_fast_state,RSDP-FAST>> state, the value of the <<tt_field,TT>> field specifies the type of the transaction it is contained in.

[[wr_payload_field]]
=== WR-PAYLOAD field

The variable-length <<wr_payload_field,WR-PAYLOAD>> field transports address and/or write data depending on the transaction.
Its presence, contents and length are described in <<transactions>>.

[[crc_field]]
=== CRC field

In <<interface_states.adoc#rsdp_robust_state,RSDP-ROBUST>> state, the <<crc_field,CRC>> field is a 6-bit value computed over all data following the <<start_field,START>> field.
Refer to <<crc_computation.adoc#crc>> for calculation of this value.

In <<interface_states.adoc#rsdp_fast_state,RSDP-FAST>> state, the <<crc_field,CRC>> field is empty (not transmitted).

[[stat_field]]
=== STAT field

The two-bit <<stat_field,STAT>> field indicates whether the operation was successful.
It is encoded as follows:

[[rd_payload_field]]
=== RD-PAYLOAD field

The variable-length <<rd_payload_field,RD-PAYLOAD>> field transports read data depending on the transaction.
Its presence, contents and length are described in <<transactions>>.

[[transactions]]
== Transaction types

The following transaction types are defined.

In <<interface_states.adoc#rsdp_robust_state,RSDP-ROBUST>> state, the transaction type is the <<tt_field,TT>> field value sent in the _previous_ transaction.

In <<interface_states.adoc#rsdp_fast_state,RSDP-FAST>> state, the transaction type is the <<tt_field,TT>> field value sent in the _current_ transaction.

An RSDP-DTM or RSDPJ-DTM must implement all of these transactions in every RSDP state it supports.

[[nop_transaction]]
=== NOP transaction

The <<nop_transaction,NOP>> transaction performs no operation and transfers no payload data.
It is used in <<interface_states.adoc#rsdp_robust_state,RSDP-ROBUST>> state as the initial transaction after a switching sequence.
The debugger can send this transaction type in the <<tt_field,TT>> field if the type of the next transaction is not known yet.
The actual <<nop_transaction,NOP>> transaction is then executed in the following step, during which the TT field is transmitted for the subsequent operation.

[[intbus_rd_transaction]]
=== INTBUS_RD transaction

The <<intbus_rd_transaction,INTBUS_RD>> transaction reads one of the DTM-internal registers described in <<intbus>>.

The <<wr_payload_field,WR-PAYLOAD>> contains the 8-bit address of the register to be accessed.
The <<rd_payload_field,RD-PAYLOAD>> contains the 32-bit data read from the register.

[[intbus_wr_transaction]]
=== INTBUS_WR transaction

The <<intbus_wr_transaction,INTBUS_WR>> transaction writes one of the DTM-internal registers described in <<intbus>>.

The <<wr_payload_field,WR-PAYLOAD>> contains the 8-bit address of the register to be accessed, followed by the 32-bit data to be written to the register.
The <<rd_payload_field,RD-PAYLOAD>> is empty.

[[dmi_transactions]]
=== DMI transactions

The <<dmi_transactions,DMI_NOP>>, <<dmi_transactions,DMI_WR>>, <<dmi_transactions,DMI_RD>>, <<dmi_transactions,DMI_WR_SA>> and <<dmi_transactions,DMI_RD_SA>> transactions provide access to the <<introduction.adoc#dmi_register,dmi>> register as specified in the _RISC-V Debug specification_, section&nbsp;6.1.5 cite:[riscv-debug-spec-1.0].
As this is the type of access that a debugger will spend most time performing, there are five transaction types to avoid transferring data that is not needed.
Each DMI transaction represents a read operation of the <<introduction.adoc#dmi_register,dmi>> register immediately followed by a write operation to the <<introduction.adoc#dmi_register,dmi>> register.
The written value is derived from the transaction type and payload data, and the read value determines the <<stat_field,STAT>> and possible <<rd_payload_field,RD-PAYLOAD>> fields.

The <<introduction.adoc#dmi_register,dmi.op>> field's write value is encoded in the RSDP transaction type, and the <<introduction.adoc#dmi_register,dmi.op>> field's read value is transported in the <<stat_field,STAT>> field of each response.

The <<introduction.adoc#dmi_register,dmi.addr>> field's write value is not sent for the <<dmi_transactions,DMI_NOP>> transaction, where its value would be ignored.
For the other DMI transactions, it is sent as part of the <<wr_payload_field,WR-PAYLOAD>> field.
It is sent in full in the <<dmi_transactions,DMI_WR>> and <<dmi_transactions,DMI_RD>> transactions, requiring the debugger to query the <<dtmcs_register,dtmcs.abits>> value before issuing these transactions.
The <<dmi_transactions,DMI_WR_SA>> and <<dmi_transactions,DMI_RD_SA>> only include a short address of two bits, retaining the remaining bits of <<introduction.adoc#dmi_register,dmi.addr>> from the last <<dmi_transactions,DMI_WR>> or <<dmi_transactions,DMI_RD>> transaction.
This allows efficient access to wide registers of a single DM (e.g. data0 to data3 or sbdata0 to sbdata3) or repeated accesses to the same registers.
Read and write addresses are not remembered separately, so a <<dmi_transactions,DMI_WR_SA>> transaction can use the upper address bits from either a <<dmi_transactions,DMI_WR>> or <<dmi_transactions,DMI_RD>> transaction, as can a <<dmi_transactions,DMI_RD_SA>> transaction.
An <<escape_sequences.adoc#enable_robust_sequence,ENABLE-ROBUST>> or <<escape_sequences.adoc#enable_fast_sequence,ENABLE-FAST>> sequence sets the address remembered by the DTM to an unknown value, so a debugger must send a full <<dmi_transactions,DMI_WR>> or <<dmi_transactions,DMI_RD>> transaction as the first DMI transaction.

The <<introduction.adoc#dmi_register,dmi.addr>> field's read value is never sent back to the debugger as it would just be a copy of the written value.

The <<introduction.adoc#dmi_register,dmi.data>> field's write value is only sent for the <<dmi_transactions,DMI_WR>> and <<dmi_transactions,DMI_WR_SA>> transactions.
It is sent in the <<wr_payload_field,WR-PAYLOAD>> field, after the address.

If the most recently executed DMI transaction was neither <<dmi_transactions,DMI_RD>> nor <<dmi_transactions,DMI_RD_SA>>, or if there was no DMI transaction since the most recent <<escape_sequences.adoc#enable_robust_sequence,ENABLE-ROBUST>> or <<escape_sequences.adoc#enable_fast_sequence,ENABLE-FAST>> sequence, <<rd_payload_field,RD-PAYLOAD>> is empty.
Otherwise, the length of <<rd_payload_field,RD-PAYLOAD>> is 32 bits.
If <<rd_payload_field,RD-PAYLOAD>> is nonempty, it contains the value of <<introduction.adoc#dmi_register,dmi.data>>, which is either the data read from the DMI or an undefined value in error cases.

[[intbus]]
== DTM-internal bus

The RSDP-DTM or RSDPJ-DTM has an internal bus with an address space for 256 32-bit registers.
Unlike the DMI bus, this bus is completely internal to the DTM and can be accessed with a fixed delay.
Command, address and data for each access are transported in a single transaction.

The following registers are defined:

[[table_intbus]]
.Registers on the DTM-internal bus
[%header,cols="1,4,1"]

| Register
| Section

| `0x00`
| IDCODE (<<idcode_register,idcode>>)
| <<idcode_register>>

| `0x01`
| DTM Control and Status (<<dtmcs_register,dtmcs>>)
| <<dtmcs_register>>

| `0x02`
| Single-Pin DIVider (<<spdiv_register,spdiv>>)
| <<spdiv_register>>

| `0x03:0x0F`

| <<extensions>>

| `0x80:0xFF`
| Reserved for vendor extensions

|===

When unimplemented registers are accessed, implementations must ignore writes and must return all-zero read data.

[[idcode_register]]
=== IDCODE (idcode, at 0x00)

The read-only <<idcode_register,idcode>> register is specified by the _RISC-V Debug specification_, section&nbsp;6.1.3 cite:[riscv-debug-spec-1.0].

[[dtmcs_register]]
=== DTM Control and Status (dtmcs, at 0x01)

The <<dtmcs_register,dtmcs>> register is described in the _RISC-V Debug specification_, section&nbsp;6.1.4 cite:[riscv-debug-spec-1.0].

The <<dtmcs_register,dtmcs.idle>> field is meaningless in RSDP interface states, as even the highest encodable number of recommended cycles is already enforced by the protocol. Therefore in RSDP interface states, the field can be ignored by the debugger. In an RSDP-DTM, the field's read value is undefined. In an RSDPJ-DTM, the field must have the read value as specified by the _RISC-V Debug specification_, section&nbsp;6.1.4 cite:[riscv-debug-spec-1.0].

The <<dtmcs_register,dtmcs.dtmhardreset>> field only resets the state of the DMI bus manager, not the communication state with the debugger.
In particular, it does not interfere with the target's response to the <<intbus_wr_transaction,INTBUS_WR>> transaction, or, in <<interface_states.adoc#rsdp_robust_state,RSDP-ROBUST>> state, the sequence counter and type of the following transaction.

An RSDP-DTM or RSDPJ-DTM compliant to this version of this specification must set <<dtmcs_register,dtmcs.version>> to the value 1.

[[spdiv_register]]
=== Single-Pin DIVider register (spdiv, at 0x02)

The read-only <<spdiv_register,spdiv>> register reads back the divider of an RSDPxSP or RSDPxCPL converter, see <<rsdpxsp.adoc#rsdpxsp_divider>>.

When the RSDP-DTM is not accessed via one of these converters, the value 0 must be read back.

== DMI bus accesses in RSDP-FAST state

<<interface_states.adoc#rsdp_fast_state,RSDP-FAST>> performs DMI bus accesses using the semantics of the <<introduction.adoc#dmi_register,dmi>> register of the JTAG-DTM.

This means that a typical single DMI write access requires two <<interface_states.adoc#rsdp_fast_state,RSDP-FAST>> transactions:

. Send <<tt_field,TT>> == <<dmi_transactions,DMI_WR>>. Send address and write data.
. Send <<tt_field,TT>> == <<dmi_transactions,DMI_NOP>>. Receive <<stat_field,STAT>>.

NOTE: See <<example_transaction_sequences.adoc#example_dmi_write>> for a full example of a single DMI bus write in <<interface_states.adoc#rsdp_fast_state,RSDP-FAST>> state.

A single DMI read access also requires two transactions:

. Send <<tt_field,TT>> == <<dmi_transactions,DMI_RD>>. Send address.
. Send <<tt_field,TT>> == <<dmi_transactions,DMI_NOP>>. Receive <<stat_field,STAT>> and read data.

NOTE: See <<example_transaction_sequences.adoc#example_dmi_read>> for a full example of a single DMI bus read in <<interface_states.adoc#rsdp_fast_state,RSDP-FAST>> state.

If multiple DMI bus accesses are scheduled, these extra transactions can be consolidated.
For example, to perform three read accesses on the DMI bus:

. Send <<tt_field,TT>> == <<dmi_transactions,DMI_RD>>. Send addr0.
. Send <<tt_field,TT>> == <<dmi_transactions,DMI_RD>>. Send addr1. Receive <<stat_field,STAT>> and rdata0.
. Send <<tt_field,TT>> == <<dmi_transactions,DMI_RD>>. Send addr2. Receive <<stat_field,STAT>> and rdata1.
. Send <<tt_field,TT>> == <<dmi_transactions,DMI_NOP>>. Receive <<stat_field,STAT>> and rdata2.

NOTE: See <<example_transaction_sequences.adoc#example_dmi_pipelining>> for a full example of multiple DMI operations in <<interface_states.adoc#rsdp_fast_state,RSDP-FAST>> state.

[[pipelining]]
== Pipelining in RSDP-ROBUST state

The <<interface_states.adoc#rsdp_robust_state,RSDP-ROBUST>> state uses the <<tt_field,TT>> field of the _previous_ transaction to determine the type of the _current_ transaction.
This is essential to guarantee detection of single-bit errors because it ensures that <<tt_field,TT>> is protected by a CRC before it is decoded and used to deduce the length of the <<wr_payload_field,WR-PAYLOAD>> and <<rd_payload_field,RD-PAYLOAD>> fields.

This delayed use of the <<tt_field,TT>> field necessitates that the debugger sends <<tt_field,TT>> = <<nop_transaction,NOP>> in a transaction when the next transaction is not known yet.
Afterwards, when it needs to execute further transactions, it will execute the <<nop_transaction,NOP>> transaction it previously requested _only_ to transport <<tt_field,TT>> for the next transaction.

For example, to read a register on the DTM-internal bus:

. <<nop_transaction,NOP>> transaction. Send <<tt_field,TT>> == <<intbus_rd_transaction,INTBUS_RD>> (for transaction 2).
. <<intbus_rd_transaction,INTBUS_RD>> transaction. Send <<tt_field,TT>> == <<nop_transaction,NOP>> (for next transaction) and address. Receive read register value.

As a result of the combination of pipelining and the semantics of the <<introduction.adoc#dmi_register,dmi>> registers, a typical single DMI bus write access requires three <<interface_states.adoc#rsdp_robust_state,RSDP-ROBUST>> transactions:

. <<nop_transaction,NOP>> transaction. Send <<tt_field,TT>> == <<dmi_transactions,DMI_WR>> (for transaction 2).
. <<dmi_transactions,DMI_WR>> transaction. Send <<tt_field,TT>> == <<dmi_transactions,DMI_NOP>> (for transaction 3), address and write data.
. <<dmi_transactions,DMI_NOP>> transaction. Send <<tt_field,TT>> == <<nop_transaction,NOP>> (for next transaction). Receive <<stat_field,STAT>>.

NOTE: See <<example_transaction_sequences.adoc#example_dmi_write>> for a full example of a single DMI bus write in <<interface_states.adoc#rsdp_robust_state,RSDP-ROBUST>> state.

A single DMI read access also requires three transactions:

. <<nop_transaction,NOP>> transaction. Send <<dmi_transactions,DMI_RD>> (for transaction 2).
. <<dmi_transactions,DMI_RD>> transaction. Send <<tt_field,TT>> == <<dmi_transactions,DMI_NOP>> (for transaction 3), address.
. <<dmi_transactions,DMI_NOP>> transaction. Send <<tt_field,TT>> == <<nop_transaction,NOP>> (for next transaction). Receive <<stat_field,STAT>> and read data.

NOTE: See <<example_transaction_sequences.adoc#example_dmi_read>> for a full example of a single DMI bus read in <<interface_states.adoc#rsdp_robust_state,RSDP-ROBUST>> state.

If multiple DMI bus accesses are scheduled, these extra transactions can be consolidated.
For example, to perform three read accesses on the DMI bus:

. <<nop_transaction,NOP>> transaction. Send <<tt_field,TT>> == <<dmi_transactions,DMI_RD>> (for transaction 2).
. <<dmi_transactions,DMI_RD>> transaction. Send <<tt_field,TT>> == <<dmi_transactions,DMI_RD>> (for transaction 3) and addr0.
. <<dmi_transactions,DMI_RD>> transaction. Send <<tt_field,TT>> == <<dmi_transactions,DMI_RD>> (for transaction 4) and addr1. Receive <<stat_field,STAT>> and rdata0.
. <<dmi_transactions,DMI_RD>> transaction. Send <<tt_field,TT>> == <<dmi_transactions,DMI_NOP>> (for transaction 5) and addr2. Receive <<stat_field,STAT>> and rdata1.
. <<dmi_transactions,DMI_NOP>> transaction. Send <<tt_field,TT>> == <<nop_transaction,NOP>> for next transaction. Receive <<stat_field,STAT>> and rdata2.

The same principle applies for a list of write operations or even mixed accesses.
The sticky behavior of the <<introduction.adoc#dmi_register,dmi.op>> field ensures that after a failed access, no further accesses are executed.

NOTE: See <<example_transaction_sequences.adoc#example_dmi_pipelining>> for a full example of multiple DMI operations in <<interface_states.adoc#rsdp_robust_state,RSDP-ROBUST>> state.

[[extensions]]
== Use of TT encodings and DTM-internal bus registers by extensions

RSDP can be extended either by standards defined by RISC-V International, or by vendor-defined extensions.

Extensions are identified and controlled by registers on the DTM-internal bus residing at the reserved addresses of <<table_intbus>>.
Each extension should define a maximum of 8 addresses in this address space.
If more registers are needed, an indirect addressing scheme should be used.

Extensions may use the <<tt_field,TT>> encodings marked as _reserved_ in <<table_tt_encoding>> under the following conditions:

 - Each extension must provide a way to enable its use of any _reserved_ <<tt_field,TT>> encoding through a register on the DTM-internal bus.
 - Following an <<escape_sequences.adoc#enable_robust_sequence,ENABLE-ROBUST>> or <<escape_sequences.adoc#enable_fast_sequence,ENABLE-FAST>> sequence, all _reserved_ <<tt_field,TT>> encodings are treated as invalid transaction requests.
   A reserved encoding remains invalid until an extension using the encoding is enabled.
 - The debugger must take care not to simultaneously enable conflicting uses of a <<tt_field,TT>> encoding by different extensions.
